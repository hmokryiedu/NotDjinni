# Functional Audit: NotDjinni

## 1. Что это за система

`NotDjinni` это backend API на `Ktor` для платформы поиска работы и найма.  
Сервис работает с `PostgreSQL`, использует `JWT`-аутентификацию, хранит refresh tokens и реализует домен вокруг:

- регистрации и логина пользователей;
- профилей соискателей;
- профилей работодателей;
- компаний;
- вакансий;
- откликов на вакансии;
- рекомендаций вакансий для соискателя.

По коду это именно серверное приложение, а не mobile/web client.

## 2. Роли и акторы

### 2.1 User

Базовый зарегистрированный пользователь системы. Может:

- зарегистрироваться;
- войти в систему;
- обновлять access token через refresh token;
- разлогиниться;
- получить свой базовый профиль;
- валидировать JWT.

### 2.2 Job Seeker

Пользователь с `seeker profile`. Может:

- создать профиль соискателя;
- обновлять и удалять профиль;
- управлять опытом работы;
- получать персональные рекомендации вакансий;
- откликаться на вакансии;
- смотреть свои отклики;
- изменять или удалять свой отклик;
- проверять, откликался ли уже на вакансию.

### 2.3 Employer

Пользователь с `employer profile`, привязанным к компании. Может:

- создать профиль работодателя;
- обновлять и удалять профиль работодателя;
- управлять вакансиями своей компании;
- смотреть вакансии своей компании;
- смотреть отклики на вакансии своей компании;
- менять статус откликов кандидатов.

## 3. Функциональные модули

## 3.1 Аутентификация и сессии

### Назначение

Обеспечивает регистрацию, логин, выпуск JWT и refresh token, ротацию refresh token и logout.

### Endpoint-ы

- `POST /auth/register`
- `POST /auth/login`
- `POST /auth/refresh`
- `POST /auth/logout`

### Основные операции

- Регистрация пользователя с именем, email и паролем.
- Логин по email и паролю.
- Генерация `accessToken` и `refreshToken`.
- Обновление access token через refresh token.
- Инвалидация refresh token при logout.

### Реализованные ограничения

- имя обязательно, не пустое, длина от `2` до `100` символов;
- email должен быть уникальным;
- пароль должен соответствовать regex `^(?=.*[a-z])(?=.*[A-Z])(?=.*\\d).{8,60}$`;
- пароль хранится в виде `SHA-256` hash;
- refresh token хранится в БД;
- срок жизни refresh token: `30` дней;
- при `refresh` старый refresh token удаляется, затем выпускается новая пара токенов;
- при истекшем refresh token он удаляется и запрос завершается ошибкой.

### Права доступа

- все endpoint-ы модуля доступны без JWT.

## 3.2 Профиль пользователя

### Назначение

Возвращает базовую информацию о текущем аутентифицированном пользователе.

### Endpoint-ы

- `GET /user`

### Основные операции

- получение текущего пользователя по `userId` из JWT.

### Права доступа

- только аутентифицированный пользователь.

### Возвращаемые данные

- `id`
- `name`
- `email`

## 3.3 Проверка токена

### Назначение

Быстрая серверная проверка валидности JWT.

### Endpoint-ы

- `GET /token/validate`

### Основные операции

- если JWT проходит верификацию, сервер возвращает успешный ответ `Token is valid`.

### Реализованные ограничения

- JWT считается валидным, если:
- подпись корректна;
- `issuer` и `audience` совпадают с конфигом;
- в токене есть claim с `userId`.

### Права доступа

- только аутентифицированный пользователь.

## 3.4 Профиль соискателя

### Назначение

Создание и управление профилем кандидата для участия в откликах и подборе вакансий.

### Endpoint-ы

- `GET /seeker/profile`
- `POST /seeker/profile`
- `PUT /seeker/profile`
- `DELETE /seeker/profile`

### Основные операции

- создание профиля соискателя;
- получение текущего профиля;
- обновление профиля;
- удаление профиля.

### Поля профиля

- `speciality`
- `desiredSalary`
- `experienceYears`
- `aboutMe`
- `jobCategory`
- `workExperience[]`

### Реализованные ограничения

- у пользователя может быть только один seeker profile;
- `speciality` не может быть пустым;
- `experienceYears` не может быть отрицательным;
- профиль привязан к текущему пользователю через `userId`;
- при `PUT /seeker/profile` список `workExperience` полностью пересоздаётся:
- старые записи удаляются;
- затем создаются новые.

### Права доступа

- только владелец профиля.

## 3.5 Опыт работы

### Назначение

Управление отдельными записями опыта работы внутри профиля соискателя.

### Endpoint-ы

- `POST /seeker/profile/experience`
- `PUT /seeker/profile/experience/{id}`
- `DELETE /seeker/profile/experience/{id}`

### Основные операции

- добавление новой записи;
- изменение существующей записи;
- удаление записи.

### Поля записи опыта

- `companyName`
- `position`
- `description`
- `startDate`
- `endDate`

### Реализованные ограничения

- запись можно менять и удалять только если она принадлежит профилю текущего пользователя;
- `companyName` не может быть пустым;
- `position` не может быть пустым;
- `startDate` не может быть в будущем;
- `startDate` не может быть позже `endDate`;
- `endDate = null` трактуется как текущее место работы.

### Права доступа

- только владелец seeker profile.

## 3.6 Компании

### Назначение

Хранение компаний, к которым могут привязываться работодатели и вакансии.

### Endpoint-ы

- `GET /company`
- `GET /company/{id}`
- `GET /company/search?name=...`
- `POST /company`
- `PUT /company/{id}`
- `DELETE /company/{id}`

### Основные операции

- получение списка компаний;
- получение компании по id;
- поиск компаний по имени;
- создание компании;
- обновление компании;
- удаление компании.

### Реализованные ограничения

- имя компании должно быть уникальным при создании;
- `website` является опциональным;
- update/delete работают по `id`.

### Права доступа

- по текущему коду все endpoint-ы модуля доступны без аутентификации.

## 3.7 Профиль работодателя

### Назначение

Связывает пользователя с компанией и даёт право управлять вакансиями этой компании.

### Endpoint-ы

- `GET /employer/profile`
- `POST /employer/profile`
- `PUT /employer/profile`
- `DELETE /employer/profile`
- `GET /employer/vacancies`

### Основные операции

- создать employer profile;
- получить свой профиль работодателя;
- обновить роль в компании;
- удалить профиль работодателя;
- получить вакансии своей компании.

### Поля профиля

- `companyId`
- `role`

### Реализованные ограничения

- у пользователя может быть только один employer profile;
- профиль можно создать только для существующей компании;
- при обновлении можно изменить только `role`;
- компания работодателя определяется профилем и используется как основа для авторизации;
- список вакансий работодателя поддерживает пагинацию `limit`, `offset`.

### Права доступа

- только владелец employer profile.

## 3.8 Вакансии

### Назначение

Публичный каталог вакансий и приватное управление вакансиями работодателя.

### Endpoint-ы

- `GET /vacancy`
- `GET /vacancy/{id}`
- `GET /vacancy/recent?limit=10`
- `GET /company/{companyId}/vacancies`
- `POST /vacancy`
- `PUT /vacancy/{id}`
- `DELETE /vacancy/{id}`
- `PUT /vacancy/{id}/status`

### Основные операции

- список вакансий с фильтрами;
- получение вакансии с деталями;
- получение последних вакансий;
- получение вакансий выбранной компании;
- создание вакансии работодателем;
- обновление вакансии;
- удаление вакансии;
- изменение статуса вакансии.

### Поля вакансии

- `title`
- `description`
- `salary.min`
- `salary.max`
- `minExperienceYears`
- `employmentType`
- `category`
- `status`

### Публичные фильтры и параметры

- `category` как repeatable query param;
- `status` как repeatable query param;
- `employment_type` как repeatable query param;
- `search`
- `company_id`
- `salary_min`
- `salary_max`
- `experience_years`
- `sort_by`
- `sort_direction`
- `limit`
- `offset`

### Поддерживаемая сортировка

- `CREATED_AT`
- `UPDATED_AT`
- `SALARY_MIN`
- `SALARY_MAX`
- `TITLE`
- `MIN_EXPERIENCE`

### Реализованные ограничения

- создать вакансию может только пользователь с employer profile;
- `companyId` вакансии при создании принудительно берётся из employer profile;
- редактировать и удалять вакансию может только работодатель из той же компании;
- изменение статуса вакансии также ограничено работодателем той же компании;
- последние вакансии возвращаются отдельным endpoint-ом;
- вакансии работодателя и компании поддерживают пагинацию `limit`, `offset`.

### Права доступа

- чтение вакансий публичное;
- создание, обновление, удаление и изменение статуса требуют JWT и employer profile.

## 3.9 Рекомендации вакансий для соискателя

### Назначение

Персонализированная выборка вакансий под seeker profile.

### Endpoint-ы

- `GET /seeker/vacancy`

### Основные операции

- получение рекомендованных вакансий для текущего соискателя;
- дополнительный текстовый поиск внутри рекомендаций.

### Реализованная логика подбора

Система строит `VacancyFilter` на основе профиля соискателя:

- `categories = [profile.jobCategory]`
- `salaryMin = profile.desiredSalary`
- `experienceYears = profile.experienceYears`
- `searchQuery = search`

После этого вызывается общий репозиторий вакансий.

### Параметры

- `search`
- `limit`
- `offset`

### Права доступа

- только аутентифицированный пользователь с seeker profile.

## 3.10 Отклики

### Назначение

Позволяет соискателю откликаться на вакансии, а работодателю просматривать кандидатов и менять статус отклика.

### Endpoint-ы

- `POST /application`
- `GET /application`
- `GET /application/{id}`
- `PUT /application/{id}`
- `DELETE /application/{id}`
- `PUT /application/{id}/status`
- `GET /application/vacancy/{vacancyId}`
- `GET /application/check/vacancy/{vacancyId}`

### Основные операции

- создание отклика;
- просмотр своих откликов;
- просмотр отклика по id;
- редактирование cover letter;
- удаление отклика;
- изменение статуса отклика работодателем;
- просмотр откликов на конкретную вакансию;
- проверка факта отклика на вакансию.

### Поля отклика

- `vacancyId`
- `jobSeekerId`
- `statusCode`
- `coverLetter`

### Реализованные ограничения

- отклик может создать только пользователь с seeker profile;
- отклик можно создать только на существующую вакансию;
- повторный отклик на ту же вакансию запрещён;
- при создании статус всегда принудительно `APPLIED`;
- владелец отклика может:
- смотреть свой отклик;
- менять cover letter;
- удалять отклик;
- работодатель может смотреть отклик, если вакансия относится к его компании;
- работодатель может получать список откликов на свою вакансию;
- работодатель может менять статус только у откликов на вакансии своей компании;
- проверка `hasApplied` для пользователя без seeker profile возвращает `false`, а не ошибку.

### Фильтры и параметры списка моих откликов

- `status`
- `sort_by`
- `sort_direction`
- `limit`
- `offset`

### Поддерживаемая сортировка

- `CREATED_AT`
- `UPDATED_AT`

### Права доступа

- `POST /application`, `GET /application`, `PUT /application/{id}`, `DELETE /application/{id}`, `GET /application/check/vacancy/{vacancyId}` требуют JWT и ориентированы на соискателя;
- `GET /application/vacancy/{vacancyId}` и `PUT /application/{id}/status` требуют JWT и employer ownership;
- `GET /application/{id}` доступен:
- владельцу отклика;
- работодателю той же компании, что владеет вакансией.

## 5. Права доступа и ownership rules

### JWT и текущий пользователь

- все защищённые endpoint-ы извлекают `userId` из JWT claim;
- токен проверяется по RSA-подписи, issuer и audience;
- отсутствие или невалидность токена даёт `401`.

### Ownership rules для seeker domain

- seeker profile принадлежит только одному user;
- work experience можно менять только внутри своего seeker profile;
- отклик можно менять и удалять только если текущий seeker profile владеет им.

### Ownership rules для employer domain

- employer profile принадлежит только одному user;
- employer profile связывает пользователя с одной компанией;
- права работодателя на вакансии и отклики определяются по `company.id`;
- если компания работодателя не совпадает с компанией вакансии, операция запрещена.

### Ownership rules для вакансий

- компания вакансии при создании не доверяется клиенту, а берётся из employer profile;
- редактирование, удаление и смена статуса вакансии доступны только работодателю той же компании.

### Ownership rules для откликов

- соискатель видит только свои отклики;
- работодатель видит только отклики на вакансии своей компании;
- доступ к отклику по id есть либо у владельца, либо у работодателя из компании вакансии.

## 7. Подтверждённые расхождения и спорные места

## 7.1 Компании доступны без auth

По бизнес-смыслу создание, обновление и удаление компаний выглядит чувствительной операцией, но в текущем коде весь модуль `/company` публичный.  
Это значит, что любой клиент без JWT может:

- создать компанию;
- изменить компанию;
- удалить компанию.

## 7.2 Диаграммы описывают больше workflow, чем реально enforce-ится кодом

Диаграммы состояний и business-flow рисуют формальные переходы статусов вакансий и откликов, но в коде нет явного state machine enforcement.

Фактически:

- `PUT /vacancy/{id}/status` принимает любой enum `VacancyStatusCode`;
- `PUT /application/{id}/status` принимает любой enum `ApplicationStatusCode`;
- проверка допустимости перехода из текущего статуса в новый отсутствует.

## 7.3 Авто-expire вакансий только задокументирован

В диаграммах есть переход `ACTIVE -> EXPIRED` как автоматическое действие системы по таймеру.  
В коде нет scheduler/job/background processing, который переводит вакансии в `EXPIRED`.

Следствие: статус `EXPIRED` существует как enum, но автоматический механизм его установки реализацией не подтверждён.

## 7.4 Диаграммы говорят о cascade delete откликов, но код делает это неявно

В state diagram для seeker profile указано, что при удалении профиля отклики каскадно удаляются.  
В репозиторном коде при `deleteProfile` удаляются:

- work experiences;
- сам seeker profile.

Явного удаления откликов на уровне repository не видно.  
Если каскад действительно работает, он должен быть зашит в схему БД/foreign key, а не в бизнес-слое. По имеющемуся проходу по коду это не подтверждено явно.

## 7.5 Удаление employer profile не удаляет вакансии

Это не расхождение, а важное бизнес-поведение, которое совпадает с диаграммами:

- удаление employer profile не удаляет вакансии;
- право на вакансии остаётся у компании, а не у конкретного работодателя.

Это важно, потому что вакансия привязана к `companyId`, а не к employer profile.

## 7.6 Обновление seeker profile полностью перезаписывает work experience

Отдельные endpoint-ы для управления опытом есть, но `PUT /seeker/profile` делает полный reset списка опыта:

- удаляет все старые записи;
- затем создаёт новые.

Это поведение может быть неожиданным для клиентов, если они ожидают partial update.

## 7.7 Refresh token и access token генерируются одним и тем же провайдером

Код использует один `TokenProvider.generate(userId)` и для access token, и для refresh token.  
Хранилище refresh token есть, но на уровне генерации нет отдельного формата/типа токена, подтверждённого по коду этого прохода.

Это не обязательно баг, но архитектурно это спорное место.

## 7.8 Password hashing реализован через SHA-256 без salt

Пароль не хранится в открытом виде, но используется простой `SHA-256` hash.  
Для production-grade auth это слабее, чем `bcrypt`, `scrypt` или `argon2`.

Это не про функционал как таковой, но это важное ограничение текущей реализации auth-модуля.

## 7.9 Порт и host зашиты под локальную сеть

В `application.yaml` заданы:

- `port: 8080`
- `host: 192.168.0.135`
- такой же адрес используется как `jwt.issuer` и `jwt.audience`.

Это признак локальной/учебной конфигурации и ограничение для развёртывания.

## 8. Итог

Система уже реализует полный базовый backend для hiring-платформы:

- auth и token lifecycle;
- два независимых пользовательских домена: seeker и employer;
- компании;
- публичный каталог вакансий;
- рекомендации вакансий;
- отклики и review flow.

Главные особенности текущей реализации:

- сильная привязка прав доступа к `company ownership` и `profile ownership`;
- публичная доступность company CRUD;
- отсутствие строгого контроля допустимых переходов статусов;
- часть поведения из диаграмм существует только как документация, а не как enforce-логика.
